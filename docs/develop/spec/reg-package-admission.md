# A5.6 — Reg package admission

This specification supplements A5.6 of `golden-ledger-repo-spec.md` for the independent declaration package.

`LeanInformationAuditInterface.Records` owns the stable occurrence, claim, dependency identity, binding certificate, result and record shapes under their `LeanInformationAudit` names. `LeanInformationAuditInterface.Store` owns their occurrence, claim and binding-record persistent extensions. Its `TemplateBinding.addRecord`, `records`, `importedRecords` and `ownedRecords` APIs transport data without assessment; origin labels identify the actual imported container or local module, independently of asserted payload owners. Records retain import order and local insertion order; `importedRecords` excludes local entries. Impl retains assessment, semantic join and imported-owner validation, proof generation, plan algorithms and JSON export. A stored `declaredValidated` payload alone grants no certification authority. The record default `compatibilityVersion = 7` and report cache release 9 have distinct existing roles and are unchanged by this relocation.

`Reg/lakefile.toml` and `Reg/lake-manifest.json` are program artifacts on the judge admission plane. The empty `Reg` library is lawful; it requires no dummy module. Its library has `srcDir = ".."`, roots `["Reg"]`, and globs `["Reg.+"]`. Outputs use `../.lake/build/reg`, and dependencies share `../.lake/packages` with the repository root.

Before cache ensure or writer admission, and in current-tree structural configuration validation (SL-015), the harness reads both manifests as data. The multiset of git tuples `(name, url, rev, inputRev, subDir, configFile, manifestFile)` must equal the root manifest, and every Reg git package is inherited. Reg has exactly three non-inherited path entries: `trureturing` at `..` with `lakefile.toml`, `leanInspectorInterface` at `../tools/lean-inspector-interface` with `lakefile.toml`, and `leanInspector` at `../tools/lean-inspector` with `lakefile.lean`; each uses `lake-manifest.json`. `packagesDir` is exactly `../.lake/packages`. A lakefile without its manifest, malformed input, or any disagreement fails closed before Lake may materialize shared dependencies.

The only declaration source families are `Reg/D5/**/*.lean`, `Reg/Support/**/*.lean`, and `Reg/Catalogs/**/*.lean`. These are content-plane executable declaration data with supporting kernel proofs, verified by `lean-build` and `lean-inspector`. The suffix after `Reg/` for a D5 mirror must satisfy the existing D5 formal path grammar and controlled stratum/domain relation. Support and catalog paths consist of CamelCase module segments. Package configs and the three source families have disjoint FILEMAP entries. These exact three content data patterns may be empty while both package configuration files are tracked and separately registered as judge programs; other empty committed patterns retain population checks. The data-verifier registry binds `lean-build` to `tools/scripts/worktree/lean-cache-run.sh` and `lean-inspector` to `tools/lean-inspector/inspect.sh`, requiring each implementation to exist and resolve to one program entry.

A Reg source is a report member, with module name obtained by removing `.lean` and replacing `/` with `.`. Report membership does not confer mathematical identity: Reg is not a stratum or a GID theory. Reg sources carry no Scribe, GID, canonical Lean header, mathematical deposit, or computational utility (SL-031) duties. They are excluded from D5 theorem candidates and mathematical truth projections. Their supporting proofs remain subject to kernel, sorry and axiom checks; a mirrored frontier path grants no exception.

Registration-only D5 addresses removed during relocation are retired explicitly through the existing canonical writer, after generating the candidate report with `make lean-report`:

```sh
PATH="$HOME/.dotnet:$PATH" dotnet run --project tools/StrataLint.Cli/StrataLint.Cli.csproj --configuration Release -- ledger-align --candidate-lean-report .lake/build/stratalint/raw-lean-report.json --retire-registration D5/S3/Observer/ObsoleteRegistration.lean
```

Repeat `--retire-registration` for each missing registration-only address. With no `--selector`, align still re-pins all retained frozen members; `--selector D5/.../Retained.lean` restricts that ordinary selection, but retained descendants of retired addresses are always included. `--add` retains its ordinary meaning. Duplicate or conflicting selectors, unknown retirement members, existing source modules, non-D5 retirement paths, mismatched state/accepted pins, and missing pinned sources without explicit retirement fail before publication. Retirement cannot be combined with `--from-accepted` or used through `ledger-append`.

The writer uses current snapshot/report truth, rejects remaining report imports of the retired addresses (including Reg imports), rebuilds retained descendants using the accepted dependency closure and current import graph, and requires the resulting accepted dependency DAG to close. It replaces current accepted snapshots and deletes the requested state fragments in the same rollback-protected publication. It emits no Revoke evidence, Reg identity, or retirement tombstone. History remains in Git. Subsequent ordinary align and `--from-accepted` cannot recreate the retired members; repeating an explicit retirement reports an unknown member and writes nothing.

The retirement selector asserts a registration-only relocation; the generic writer cannot infer that classification or proof preservation from accepted statement hashes. Content reconciliation must establish the pre/post declaration mapping, preserve mathematical statement/proof bytes in retained D5 owners, account for statement-id changes caused by extracted metadata, and rebuild generated Reg proofs under Lean. It must also migrate or remove the retired addresses' Scribe documents and coverage references. Existing Scribe validation (`DescribeRepositoryValidator`/`DeclarationCatalog`) and digestion current-edge validation (`CurrentEdgeValidator`/`FrozenStatementIndex`) own those checks in the final current/delta delivery. Ledger-align does not load a second document/coverage inventory or certify those checks; successful retirement alone is not completed content reconciliation.

The report selection includes optional `Reg/**/*.lean` and requires the two package configuration files once introduced. An empty Reg adds no module rows. A producer that embeds the full `lean-report-inputs.json` hash in raw evidence changes raw bytes when these registrations are added; byte equality therefore depends on the independent report-cache-release change removing those redundant input records. This admission does not change report version, reuse, or per-module traces.

`make lean` demands the root defaults (including D5 and judge audits) and the independent Reg default. Explicit `LEAN_TARGETS` retain their scope: `Reg`, `Reg.*`, `+Reg.*`, and `@reg` package targets are built in the Reg workspace; other targets stay in the root workspace. A failure in either demanded build fails the entrypoint. `make lean-report` uses the Reg workspace when the declaration package is present; its report facet demands both root and Reg defaults and reports the registered modules of both packages, including an empty Reg. After `make lean-cache-ensure`, a direct Reg-cwd Lake build is supported. The cache reader/writer validates shared-manifest agreement before either supported entrypoint lets Lake materialize Reg dependencies.

Repository root and Lake package ownership are distinct. Judge source IO locates the nearest ancestor containing the root `lakefile.toml` and `lean-toolchain` at runtime. Facets resolve the same root from the current workspace package and keep report coordination and artifacts at `<repository>/.lake/build/lean-inspector`; compiler outputs remain owned by their Lake packages, including `<repository>/.lake/build/reg`. Native commands run at the repository root with Lake's toolchain environment. Evidence retains logical repository-relative source paths, with Interface sources under `tools/lean-inspector-interface`. No build-host absolute root is embedded in an olean, so copied artifacts support repository relocation and roots containing spaces. Source hashes, export reassessment, whole-report reuse, semantic version 9 and module traces retain their existing contracts.

A sealing root's `RootCatalogContract` supplies its exact expected occurrences, an independent source snapshot, the baseline rows that source must retain, and an optional public companion prefix. The stable record and occurrence row types live in `LeanInformationAuditInterface.RootContract`; `RootCatalogs.declare` installs a contract for the compiling root before registration or sealing. Expected membership, statement identities, and contributor modules are compared with actual registry output. The source snapshot must retain every baseline row in all three coordinates. Neither expected rows nor baseline rows are derived from the registry being checked.

Generic seal and companion consumers resolve this contract by the compiling root's identity. The current catalog supplies the existing InformationRoot and SharedInformationRoot contracts from their independently supplied snapshots. A registration module can publish imported-theorem companions under its own qualified prefix, for example `companionPrefix := some rootId`; downstream modules refer to those genuine declarations and compiler ownership stays with the registration module. Without an explicit public prefix, imported companions remain private to their compilation. An imported root contract does not select a downstream root, and duplicate declarations of a root contract are rejected.
