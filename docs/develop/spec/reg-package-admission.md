# A5.6 — Reg package admission

This specification supplements A5.6 of `golden-ledger-repo-spec.md` for the independent declaration package.

`Reg/lakefile.toml` and `Reg/lake-manifest.json` are program artifacts on the judge admission plane. The empty `Reg` library is lawful; it requires no dummy module. Its library has `srcDir = ".."`, roots `["Reg"]`, and globs `["Reg.+"]`. Outputs use `../.lake/build/reg`, and dependencies share `../.lake/packages` with the repository root.

Before cache ensure or writer admission, and in current-tree structural configuration validation (SL-015), the harness reads both manifests as data. The multiset of git tuples `(name, url, rev, inputRev, subDir, configFile, manifestFile)` must equal the root manifest, and every Reg git package is inherited. Reg has exactly three non-inherited path entries: `trureturing` at `..` with `lakefile.toml`, `leanInspectorInterface` at `../tools/lean-inspector-interface` with `lakefile.toml`, and `leanInspector` at `../tools/lean-inspector` with `lakefile.lean`; each uses `lake-manifest.json`. `packagesDir` is exactly `../.lake/packages`. A lakefile without its manifest, malformed input, or any disagreement fails closed before Lake may materialize shared dependencies.

The only declaration source families are `Reg/D5/**/*.lean`, `Reg/Support/**/*.lean`, and `Reg/Catalogs/**/*.lean`. These are content-plane executable declaration data with supporting kernel proofs, verified by `lean-build` and `lean-inspector`. The suffix after `Reg/` for a D5 mirror must satisfy the existing D5 formal path grammar and controlled stratum/domain relation. Support and catalog paths consist of CamelCase module segments. Package configs and the three source families have disjoint FILEMAP entries. These exact three content data patterns may be empty while both package configuration files are tracked and separately registered as judge programs; other empty committed patterns retain population checks. The data-verifier registry binds `lean-build` to `tools/scripts/worktree/lean-cache-run.sh` and `lean-inspector` to `tools/lean-inspector/inspect.sh`, requiring each implementation to exist and resolve to one program entry.

A Reg source is a report member, with module name obtained by removing `.lean` and replacing `/` with `.`. Report membership does not confer mathematical identity: Reg is not a stratum or a GID theory. Reg sources carry no Scribe, GID, canonical Lean header, mathematical deposit, or computational utility (SL-031) duties. They are excluded from D5 theorem candidates and mathematical truth projections. Their supporting proofs remain subject to kernel, sorry and axiom checks; a mirrored frontier path grants no exception.

The report selection includes optional `Reg/**/*.lean` and requires the two package configuration files once introduced. An empty Reg adds no module rows. A producer that embeds the full `lean-report-inputs.json` hash in raw evidence changes raw bytes when these registrations are added; byte equality therefore depends on the independent report-cache-release change removing those redundant input records. This admission does not change report version, reuse, or per-module traces.

`make lean` demands the root defaults (including D5 and judge audits) and the independent Reg default. Explicit `LEAN_TARGETS` retain their scope: `Reg`, `Reg.*`, `+Reg.*`, and `@reg` package targets are built in the Reg workspace; other targets stay in the root workspace. A failure in either demanded build fails the entrypoint. `make lean-report` uses the Reg workspace when the declaration package is present; its report facet demands both root and Reg defaults and reports the registered modules of both packages, including an empty Reg. After `make lean-cache-ensure`, a direct Reg-cwd Lake build is supported. The cache reader/writer validates shared-manifest agreement before either supported entrypoint lets Lake materialize Reg dependencies.

Repository root and Lake package ownership are distinct. Judge source IO locates the nearest ancestor containing the root `lakefile.toml` and `lean-toolchain` at runtime. Facets resolve the same root from the current workspace package and keep report coordination and artifacts at `<repository>/.lake/build/lean-inspector`; compiler outputs remain owned by their Lake packages, including `<repository>/.lake/build/reg`. Native commands run at the repository root with Lake's toolchain environment. Evidence retains logical repository-relative source paths, with Interface sources under `tools/lean-inspector-interface`. No build-host absolute root is embedded in an olean, so copied artifacts support repository relocation and roots containing spaces. Source hashes, export reassessment, whole-report reuse, semantic version 9 and module traces retain their existing contracts.
